# Group clinic access: current assumptions and contracts

Source inspection: 2026-10-16. Dashboard source revision: `d96152d0a8c4f4e2fe65892d5d873291353d8f72`. Website source revision: `eda78ba87601db5f00fe8c218ce1acd36e6b0b1d`. This is an inventory of the inspected code and approved planning decisions, not a proposed model or proof of deployment.

## Shared boundary

The [shared platform context](https://github.com/findmydoc-platform/platform-architecture/blob/main/03_context_and_scope.md) places clinic business data and authorization in Website/Payload. The Dashboard has its own origin, Supabase session, and BFF. The [Website integration contract](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/docs/integrations/clinic-dashboard-api.md#L8-L39) says the Dashboard cannot send an authoritative clinic, role, or actor value, and a new shared route or DTO requires coordinated changes in both repositories. The [Dashboard contract](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/docs/authentication-and-bff.md#L56-L94) keeps browser calls behind specific same-origin BFF routes. Neither application document establishes per-capability Preview or Production availability; the [Dashboard capability table](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/docs/authentication-and-bff.md#L15-L46) marks those checks open.

## Website/Payload assumptions

- A platform-controlled clinic application provisions one clinic and initial staff member. The [application collection](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/collections/ClinicApplications.ts#L9-L29) limits direct access to platform staff and runs the provisioning hook after change. The [provisioning function](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/features/clinicOnboarding/provisionClinicOnboarding.ts#L54-L116) creates a clinic with approved participation and pending public status, then an approved `clinicStaff` record whose `clinic` is that one clinic ID.
- The [ClinicStaff relation](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/collections/ClinicStaff.ts#L216-L232) is `hasMany: false`. Platform staff alone may assign it. The collection's [read filter](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/collections/ClinicStaff.ts#L29-L51) gives clinic staff records from their assigned clinic. No clinic-group collection appears in the inspected [Payload collection registry](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/payload.config.ts#L527-L565); this is a source-revision observation, not a statement about deployed data.
- The [access-state lookup](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/auth/utilities/clinicAccessState.ts#L18-L82) accepts one approved, synchronized staff principal with account-completion evidence and one assigned participation-approved clinic. The [assignment helper](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/access/utils/getClinicAssignment.ts#L19-L40) returns a single numeric clinic ID or null. Reusable [scope filters](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/access/scopeFilters.ts#L21-L107) use equality against that ID for clinic resources and use its presence to permit some mutations. The full access surface extends beyond this helper, so these are examples rather than an exhaustive list of affected permissions.
- The [bootstrap DTO](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/features/clinicDashboard/bootstrap.ts#L23-L47) contains one `clinic` object and one flat capability list. Its [resolver](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/features/clinicDashboard/bootstrap.ts#L105-L145) derives that clinic from the current access state. [Request revalidation](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/features/clinicDashboard/authorization.ts#L12-L37) binds each request to the current token and principal. The [integration contract](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/docs/integrations/clinic-dashboard-api.md#L41-L110) defines private `no-store` bootstrap behavior and says capabilities do not replace authorization of later reads and changes.
- Domain handlers currently derive their clinic from that one authorized bootstrap. Examples: [profile](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/endpoints/clinicDashboardProfile.ts#L30-L45), [gallery](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/endpoints/clinicDashboardGallery.ts#L44-L58), and [reporting](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/features/clinicDashboard/reporting/service.ts#L348-L370). Reporting filters inquiries and reviews by that clinic ID in the same [service](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/features/clinicDashboard/reporting/service.ts#L231-L261).

## Dashboard assumptions

- The strict [authenticated context schema](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/auth/model/auth.ts#L3-L35) accepts one clinic and one capability list. Its [return-target parser](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/auth/model/auth.ts#L54-L82) permits the home route or an inquiry ID, with no clinic identity in the link. The [bootstrap client](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/auth/server/payload-bootstrap.ts#L72-L121) validates that shape and requires private, `no-store` response headers.
- [Route authorization](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/auth/server/route-access.ts#L21-L70) derives `clinicId` from `access.context.clinic.id`, not a request-selected clinic. The [provider composition](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/data-provider-composition.ts#L49-L95) binds a token and clinic ID to individual domain providers. [Reporting](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/dashboard/server/reporting-actions.ts#L44-L70), [gallery](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/clinic-profile/server/clinic-gallery-actions.ts#L85-L102), and [inquiries](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/messages/server/actions.ts#L222-L235) pass the authorized ID into their providers.
- The visible [location selector composition](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/workspace/ClinicDashboardWorkspaceComposition.tsx#L292-L305) uses multiple locations only for reporting demo input. In normal mode, the [selector](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/workspace/ClinicDashboardWorkspaceComposition.tsx#L418-L427) is bound to the authenticated clinic and disabled for switching. Its [client controller](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/workspace/useClinicDashboardController.ts#L24-L41) stores a selected location for demo presentation, not an authorized backend context.

## Notification interaction constraints

- The existing [notification Wayfinder map #166](https://github.com/findmydoc-platform/clinic-dashboard/issues/166) records Website ownership of durable occurrences and personal read receipts, Dashboard BFF delivery, current authorization, exact navigation, and separate activation. It also says the map does not authorize changing the approved notification product specification.
- [Authorization decision #173](https://github.com/findmydoc-platform/clinic-dashboard/issues/173#issuecomment-6102264576) requires current Website permission checks for feed rows, counts, groups, read receipts, and exact target opening. It requires discarding loaded notification information on detected clinic change or access loss, while allowing marked stale data after a temporary failure without known access loss. Its `clinic change` wording predates the group-manager product decision to show notifications from all authorized clinics. This overlap needs a Wayfinder decision; the inventory does not resolve it.
- At the inspected Dashboard revision, the [notification BFF route](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/notifications/server/actions.ts#L132-L181) passes one bootstrap `clinicId` into the provider. The [Payload provider](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/notifications/server/payload-notifications.ts#L13-L27) requires an ID but its GET and POST calls do not include a clinic selector. The [notification item schema](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/notifications/model/notification-schema.ts#L91-L143) has source record and destination IDs but no source clinic identifier or name in the display envelope. The [UI open handler](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/src/features/clinic-dashboard/workspace/ClinicDashboardWorkspaceComposition.tsx#L327-L383) handles unsaved-work guards and opens an inquiry or review within the current scope; it has no cross-clinic selection step.
- The inspected Website source revision registers no notification collection or focused notification endpoint in its [Payload config](https://github.com/findmydoc-platform/website/blob/eda78ba87601db5f00fe8c218ce1acd36e6b0b1d/src/payload.config.ts#L527-L565). The Dashboard's [runtime note](https://github.com/findmydoc-platform/clinic-dashboard/blob/d96152d0a8c4f4e2fe65892d5d873291353d8f72/docs/authentication-and-bff.md#L479-L481) describes its notification BFF implementation but explicitly does not establish Preview or Production activation. Verify both repositories' current heads before treating this inventory as a release-state report.

## Open questions handed to Wayfinder

The inventory locates the one-clinic assumptions. It does not choose a group schema, role representation, selected-clinic contract, migration, or notification contract change. Those decisions must account for the approved product rules and the existing notification map's authorization behavior before implementation tickets are written.
