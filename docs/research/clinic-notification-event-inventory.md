# Clinic notification source events and contract gaps

Research date: 2026-10-05
Ticket: [Inventory notification source events and contract gaps](https://github.com/findmydoc-platform/clinic-dashboard/issues/167)
Map: [Plan the Clinic Dashboard notification center](https://github.com/findmydoc-platform/clinic-dashboard/issues/166)

## Scope and evidence

This note inventories the seven event groups in the approved [Notification Center product specification][prd]. It records source facts and contract gaps. It chooses no notification architecture and changes no approved product behavior.

Sources were read again on the research date:

- Clinic Dashboard at `2ff4d5405bfef6b44841bc14028423959201048e`.
- Website at `eda78ba87601db5f00fe8c218ce1acd36e6b0b1d`.

- The approved Notion specification, fetched on 2026-10-05 with page last-edited time `2026-10-05T15:49:54.050Z`.

The source links below are pinned to these revisions. Uncommitted work in the application checkouts was excluded. The unapproved `docs/plans/clinic-notification-center.md` was not used as a requirements source. No environment acceptance run, product implementation, migration, or deployment was performed.

The shared architecture assigns business data and authorization to Website/Payload. Dashboard browser interactions stay behind its server BFF. It explicitly leaves capability rollout evidence open. [Architecture][architecture]

## Findings

All seven groups have relevant persisted source behavior. Six have at least part of a clinic-readable projection. The final outcome of an inquiry moderation appeal exists internally but has no participant-readable outcome or decision timestamp. The existing notification center consumes demo records and browser session read state. It has no source-backed provider in the domain composition. [Inquiry appeals][inquiry-appeals] [Participant moderation contract][moderation-dto] [Demo records][demo] [Session storage][session] [Existing center][existing-center] [Composition][composition]

Existing inquiry read positions and `clinicNotificationSequence` cannot provide the approved center semantics. Internal notes also advance that sequence; moderation events do not. Inquiry read state belongs to the communication workflow, while the PRD requires a separate personal notification read state. [Inquiry sequence][message-command] [Internal notes][internal-notes] [Moderation activity][moderation-activity] [PRD][prd]

## Clinic/staff scope and display fields

Inquiry queue/detail derive clinic access from the current approved staff principal and filter the inquiry by that clinic. The current actor key is `clinicStaff:<id>`. Inquiry read positions are bound to that actor and inquiry. Reviews, response workflows, and appeal workflows use the assigned clinic scope. Native review history is platform-only; the clinic publication-history endpoint is the supported safe alternative. [Inquiry authorization][inquiry-auth] [Inquiry read contract][inquiry-contract] [Review access][review-access] [Publication history][publication-history]

The center can use only the fields the current clinic projection permits:

- Inquiry `id`, `createdAt`, clinic descriptor, and permitted `patientName`. Identity removal changes the name to `Deleted patient` and makes contact unavailable. Message timeline suppresses deleted actor names and restricted/deleted content. The inquiry queue's `preview` can contain message text or an attachment name, so it must not be copied into the center. The PRD keeps text and file previews in the underlying record. [Inquiry projection][inquiry-projection] [Timeline][timeline] [PRD][prd]
- Review `id`, rating, and safe `publicAuthorName`, with Dashboard fallback `Anonymous patient`. Publication history suppresses historical names/text that no longer match the safe current projection. Current removal or withdrawal suppresses historical text. An event record must not preserve an old unsafe display snapshot without current authorization and sanitization. [Review mapping][review-mapping] [Safe publication history][publication-history] [PRD][prd]
- Neutral inquiry restriction/restoration state. Only the affected actor receives the safe category, optional measure end, and appeal path. Reporter identity, report text, and internal moderation audit data never enter participant projections. Review appeal decision reason is already a clinic-readable workflow field; inquiry appeal internal reason is not. The center's required event label/name/time does not require copying decision reasons or submission text. [Inquiry moderation contract][inquiry-contract] [Participant projection][participant-projection] [Dashboard history][dashboard-history] [PRD][prd]

Inquiry moderation has a narrower actor scope than ordinary clinic content. `affectedClinicStaff` identifies an individual staff actor; the appeal path is shown only when the current actor matches that affected participant. An identity messaging suspension follows the affected actor across conversations. One neutral audit occurrence is appended to the case's inquiry, not every affected conversation. Recipient visibility for each neutral measure and for the clinic's final appeal decision must therefore be explicit in the notification authorization contract. The PRD's current-permission requirement remains binding. [Participant projection][participant-projection] [Moderation activity][moderation-activity] [PRD][prd]

## Identifiers, timestamps, and bounded reads

Use of existing collection IDs in the inventory does not permit use of the hidden `stableId` field in runtime contracts. Its owner explicitly reserves it for seed/import reproducibility and excludes runtime filters, URLs, and user-facing queries. Native document IDs and native version IDs already appear in the supported runtime projections. A notification source key still needs collection/category namespacing and an occurrence discriminator for mutable workflows. [Identifier rule][stable-id] [Publication history][publication-history] [Dashboard history][dashboard-history]

Inquiry `changeCursor` values describe complete query/detail projections. They are opaque change markers, not durable delivery offsets or event identities. Review publication history has a keyset cursor bound to the current review revision; a changed review returns `HISTORY_CHANGED`. Dashboard reads response and appeal history with a limit of 1,000 versions. These existing reads do not define a cross-domain feed or a completeness guarantee for notifications after absence. [Inquiry contract][inquiry-contract] [Publication history][publication-history] [Dashboard history][dashboard-history]

Native `createdAt` identifies stored message/audit occurrences. `recordedAt` identifies a native review/workflow version. Business `reviewDate`, mutable `updatedAt`, current status, and collection ID alone are not reliable substitutes for the publication/decision occurrence. Same-status edits and repeated moderation writes need a defined eligibility rule; only qualifying new transitions should become notification occurrences. This is an inference from the owner histories and mutation hooks, not an existing event contract. [Response workflow][response-workflow] [Appeal workflow][appeal-workflow] [Current Dashboard schema][review-adapter]

Timed moderation restoration has two relevant times. Safe state expires according to `effectiveUntil`; the stored restoration audit event is generated when reconciliation runs and carries its own native creation time. Current clinic detail handling schedules that reconciliation after the response. No source here establishes that this creates a restoration occurrence within one minute of expiry when no detail request is made. The event contract must distinguish effective time from recording time, and the delivery/rollout decision must establish the approved freshness behavior. [Inquiry appeals][inquiry-appeals] [Reconciliation scheduling][reconciliation]

## Missing contracts exposed by this inventory

1. **Occurrence identity and eligibility.** Define qualifying owner transitions, a stable source identity for each occurrence, and duplicate behavior. Include inquiry plus first text, repeated review-response decisions, same-status appeal edits, review removal paths, and expiry versus recording time. Current records and histories supply evidence but do not provide one approved notification event contract. See the source links in the inventory above.
2. **Safe inquiry appeal result.** Expose the affected clinic participant's terminal outcome and occurrence time through an authorized projection. Current private case/events contain those facts; participant DTOs omit them. Specify actor scope and keep reporter/internal audit details excluded. [Moderation events][moderation-events] [Participant moderation contract][moderation-dto]
3. **Structured measure occurrences.** Preserve event type and the source occurrence identity across the Website-to-Dashboard contract. Current Dashboard inquiry mapping converts system event type into display text. Identity restrictions also require explicit actor/conversation recipient scope. [Dashboard mapping][inquiry-adapter] [Participant projection][participant-projection]
4. **Durability and personal read state.** Provide post-activation capture while users are absent, a 90-day event lifetime, separate staff read state, per-person message grouping, and captured event membership for single/bulk read actions. Existing browser session state and communication read positions do not implement these rules. [Existing center][existing-center] [Inquiry sequence][message-command] [PRD][prd]
5. **Complete reads and delivery.** Define paginated notification history, an authorized total unread-entry count independent of loaded rows, stable ordering, retry/error behavior, and the within-one-minute delivery evidence. Neither source history cursors nor latest inquiry/review snapshots establish these guarantees. [Inquiry contract][inquiry-contract] [Dashboard history][dashboard-history] [PRD][prd]
6. **Current authorization and unavailable targets.** Define current clinic/staff/field scope on notification reads and read acknowledgements, plus a safe result for withdrawn, removed, rejected, deleted, or newly forbidden targets. Older source versions can contain fields no longer safe to display. [Publication history][publication-history] [Inquiry projection][inquiry-projection] [PRD][prd]

These are engineering decisions needed to satisfy the approved product input. This note does not reopen event categories, personal reads, grouping, 90-day retention, one-minute freshness, or the no-backfill boundary.

## Environment evidence and exclusions

For every inventory row, code presence is established at the pinned revisions; Preview and Production availability remain unverified by this research. The Dashboard capability table explicitly lists inquiry and review availability as open for both environments. The shared architecture also leaves per-capability deployment open. A selected Payload adapter, native schema, local fixture, test, or build would not establish deployed authorization or event delivery. [Capability status][runtime-status] [Architecture][architecture]

The approved exclusions remain unchanged: reminders, announcements/promotions, email, push, patient replies to reviews, historical backfill, and new moderation workflows. Existing response data belongs to clinic-authored responses; it supplies no patient-reply trigger. New reports and intermediate appeal states are not among the approved triggers. [PRD][prd] [Review process][review-process] [Inquiry moderation contract][inquiry-contract]
